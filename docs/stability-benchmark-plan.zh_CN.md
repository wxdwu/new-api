# 网关稳定性量化测试方案

日期：2026-09-05。状态：方案与源码核对完成；2026-09-05已恢复云端访问、完成12轮共5400次隔离对照测试并清理临时环境。本文是实验设计，实际执行条件与结果以 `docs/stability-benchmark-results.zh_CN.md` 为准。

## 1. 要回答的问题

在相同机器、渠道资源、请求样本和到达速率下，启用或调整某项机制，是否提高用户正常完成Agent调用的比例？代价是多少额外上游调用、延迟或主动拒绝？

用户补充的业务口径：一切无法正常调用Agent的情况均归为失败，曾见过类似`error response body`的提示；尚无确切错误正文、HTTP状态或发生层证据。主指标必须覆盖用户实际发起的Agent调用，不能仅统计网关HTTP请求或收到响应头。错误类型可拆分定位，但不能因此将失败从业务分母中移除。

八类机制都可以量化，但必须区分容量测试、对照实验和故障注入。仅测当前版本能承受多少请求，不能证明某功能带来了多少改善；仅让模拟上游返回故障，也不能证明生产容量。

## 2. 测试链路与环境

```text
独立压测机：按预定时间发送用户请求并逐条记录结果
  → 测试入口 Nginx
  → new-api：资源检查 → 认证 → 用户限流 → 选渠道/Key → Relay
  → 可控模拟上游 A/B：容量、首段延迟、输出速率、故障时间表
  → new-api 转发响应
  → 压测机：验证正文/流结束、计算首段和完整响应耗时

旁路观察：网关/入口日志、MySQL、Redis、进程与容器资源、模拟上游尝试记录
```

- 使用与服务器部署相近的测试实例、独立数据库和Redis实例。承载真实用户的服务器本轮仅作为观察对象，不安排破坏性实验。
- 同一台服务器新增容器仍然共享CPU、内存、磁盘和网络，不能当成资源已隔离。容量测试应独占资源或明确配额，并记录其他负载。
- 先用模拟上游验证机制和网关容量，再在明确流量/费用预算内对真实上游做小规模验证。模拟服务必须实现被测接口的有效JSON/SSE、完成标志和所需usage等字段。
- 不压 `/api/status` 来代替消息接口；用户通过 `/v1/responses` 发消息时优先覆盖该路径，使用其他协议时另设场景。保留Nginx这一实际入口，直连网关只作定位用对照。
- 准备独立测试用户及足够测试额度。多把Token属于同一用户时仍共享用户限流，不能据此模拟多个独立用户。
- 测试实例的通知出口应禁用或接入本地收件器，故障摘除实验不应发送真实邮件、群消息或Webhook。测试凭据由本地安全渠道注入，不写入报告或原始采样文件。

## 3. 执行前记录实际配置

记录版本/镜像标识、CPU/内存配额、实例数、Nginx超时与大小限制、数据库连接池、Redis是否实际启用，以及下列脱敏配置：

- 模型、分组、候选渠道、优先级、权重、Key数量及是否共享上游配额。
- 渠道亲和、指定渠道、自动跨分组行为和内存缓存是否启用。
- `RetryTimes`、可重试状态码、自动禁用/恢复、每个渠道AutoBan及探测周期。
- 用户总请求桶与成功请求窗口的开关/额度，系统资源检查阈值，流式及整体超时。

源码初始值不是线上有效值：`common/constants.go`中重试次数初始为0、自动禁用/恢复初始关闭；`setting/rate_limit.go`中模型请求限流初始关闭。数据库Option和环境配置可能覆盖它们。恢复探测也需要确认后台任务实际运行。

先用少量请求验证机制确实触发，再进行负载实验。资源阈值应核对读取的是宿主机还是容器可见指标，不能默认它准确对应容器配额。

## 4. 统一统计口径

主要以实际Agent客户端/测试驱动器为用户调用结果的事实来源，并辅以HTTP压测客户端。每次Agent调用分配运行ID，其内部每个模型请求分配测试ID，再与网关Request ID、上游尝试关联。先验证关联信息确实可以贯通，不能假定任意自定义Header都会透传。

一次Agent调用可能包含多轮模型请求、工具执行和客户端重试。分别记录Agent调用、模型请求、上游尝试三层数量；不能把请求失败率直接改名为Agent失败率。最终业务验证需经过实际Agent客户端/运行流程。固定Agent版本、任务集、工具环境、重试策略及完成期限，以正常终止/预设必要步骤完成为判据；工具报错、协议解析错误、客户端错误等导致调用最终失败也计入总失败，再分类评估网关机制能覆盖多少。内部错误若被自动恢复且最终正常完成，单列为已恢复错误，不记为最终Agent失败；未经恢复的任何阻断均计入。

| 指标 | 定义与解释 |
| --- | --- |
| Agent调用失败率（主指标） | 在预设完成期限内无法正常运行/完成、最终报错或异常中断的Agent调用数 / 测试驱动器实际发起的Agent调用数；发起后、请求到达网关前的失败也包含在内 |
| 网关请求未成功率 | 在预设请求期限内未取得符合测试要求的完整响应数 / 实际发出的逻辑模型请求数；包括429、503、超时和流中断，是定位与机制实验指标 |
| 正常用户未成功率 | 预先定义的正常流量组中未成功数 / 该组实际发出数；不能事后删除被限流的正常请求 |
| 有效吞吐 | 稳态窗口内完整成功响应数 / 窗口秒数；与进入网关的RPS、上游尝试RPS分别展示 |
| 首段延迟 | 从发出请求到收到第一段有效业务输出；HTTP响应头、SSE心跳、空事件不算首段 |
| 完整响应P95/P99 | 完整成功请求耗时分位数，同时报告失败/超时量与期限；避免快速拒绝拉低总体平均耗时造成假改善 |
| 重试放大倍数 | 用户请求导致的上游尝试总数 / 实际发出的逻辑请求数；自动健康探测另计，不混入 |
| 重试补救比例 | 首次尝试失败、最终成功的逻辑请求数 / 首次尝试失败的逻辑请求数 |
| 故障摘除时间 | 上游故障开始到网关状态禁用/路由排除的时间，另外记录状态传播期间新发往故障渠道的请求 |
| 探测恢复时间 | 上游恢复可用到网关重新启用并实际成功分流的时间 |
| 资源恢复时间 | 停止异常负载后，在途数、连接数、goroutine和内存等回到预设可接受范围所需时间 |

每条请求记录Agent运行ID、运行编号、测试ID、用户类别、请求起止时间、首段时间、HTTP状态、业务错误分类、流是否完成、失败阶段和尝试次数。Agent侧另记最终状态、模型请求数、工具步骤状态和是否经过自动恢复。请求正文、回答正文、凭据和真实账号信息不落盘；只保存判断所需的脱敏字段。

流式HTTP 200只代表响应已开始，不足以证明用户收到完整回答。按当前协议验证完成事件、业务状态及测试所需输出；不能仅看EOF或单一结束字符串。网关 `service/log_info_generate.go:appendStreamStatus`记录的`other.stream_status`可作辅助证据，仍需客户端验证。

故意取消和非法大请求使用独立场景/分组，报告其取消回收与拒绝行为，不并入正常调用组成功率；正常任务中的意外取消/超限仍计入失败。客户端/SDK自动重试在HTTP机制对照阶段关闭；最终Agent验证保留并固定真实客户端策略，同时统计逻辑调用、客户端重发和网关上游尝试。

计划发送但压测机没有发出的请求单独报告；不能偷偷从计划负载中消失，也不能算作服务器已接收的失败。固定每秒到达的实验可用k6 arrival-rate执行器，避免服务变慢时压测程序也随之减少发送。参见[k6开放与闭合负载模型](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)和[未能启动的迭代](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/)。

普通HTTP可用k6做状态和正文检查；流式需要能逐事件读取的采集客户端或经验证的工具，实施时先用已知时序的模拟流验证首段、完成、中断、取消测量。不能把普通HTTP等待响应头的时间直接当首Token延迟。k6检查项可参考[官方Checks文档](https://grafana.com/docs/k6/latest/using-k6/checks/)。

## 5. 八类机制的对照设计

| 机制 | 控制与实验 | 重点指标 | 源码锚点与解释边界 |
| --- | --- | --- | --- |
| 优先级与加权随机 | 相同A/B渠道及容量，先使用偏斜权重，再使用与容量匹配的权重；固定其余机制。备用优先级另做故障切换场景 | 完整失败率、有效吞吐、渠道分布、在途量和上游429 | `model/channel_cache.go:CacheGetRandomSatisfiedChannel`；只在当前优先级层内分流，不会自动按实时负载改权 |
| Redis Lua令牌桶 | 多个正常用户加一个突发用户，同一流量时间表下开/关用户总请求限流；成功请求窗口单独控制，避免先挡住请求 | 正常用户完整成功率、所有用户429/503、有效吞吐、异常用户获准请求量 | `middleware/model-rate-limit.go:redisRateLimitHandler`、`common/limiter/lua/rate_limit.lua`；用户级速率与突发限制，不是全系统并发上限 |
| 错误分类与有限重试 | 固定渠道资源与故障时间表，重试0次对比1次；暂时关闭摘除，注入明确可重试错误；另设所有上游同时故障场景 | 最终失败率、补救比例、上游放大倍数、P95/P99 | `controller/relay.go:Relay/shouldRetry`；备用要有余量，相关故障下重试可能增加负载 |
| 故障摘除与探测恢复 | 固定重试和分流配置，某渠道在预定时刻持续出现符合禁用规则的错误、随后恢复；比较自动摘除关闭/开启 | 摘除与恢复时间、故障期间用户失败、故障渠道新请求、探测次数 | `service/channel.go:ShouldDisableChannel/ShouldEnableChannel`、`controller/channel-test.go:performChannelTests`；受全局开关、渠道AutoBan、探测及缓存传播影响 |
| 多Key随机/轮询 | 先固定相同Key池比较选取策略；另作单Key与多Key资源扩展实验，模拟独立配额和共享配额两种上游 | 每Key分布、上游429、最终失败、有效吞吐 | `model/channel.go:GetNextEnabledKey`；多Key可能共享账号/组织额度，增加Key不等于增加容量；资源扩展收益需单独归因 |
| 系统资源阈值检查 | 独立测试环境中固定请求曲线，开/关检查，逐步超过舒适负载后降回正常；先以受控阈值验证触发，不必先压到崩溃 | 主动503、有效吞吐、尾延迟、重启次数、过载后的恢复时间 | `middleware/performance.go:checkSystemPerformance`、`common/system_monitor.go`；周期快照，不保证阻挡短时峰值，不会自动扩容 |
| 流式缓冲、超时、取消 | 分别注入无后续数据的上游、慢读客户端、主动取消；比较不同超时配置，或有明确修复的前后版本 | 完整流成功率、超时回收时间、取消后仍在途量、goroutine/连接/内存曲线 | `relay/helper/stream_scanner.go:StreamScannerHandler`；缓冲与取消没有统一开关，不为对照删除保护；本地关闭连接不保证真实上游停止生成/计费 |
| 缓存、连接复用、大小限制 | 拆成三个实验：特定缓存冷/热或开/关；复用连接策略；固定比例超大请求与正常请求混合 | DB查询/等待、连接新建数、延迟、CPU/内存峰值、413、正常请求成功率 | `model/channel_cache.go`、`service/http_client.go:InitHttpClient`、`common/body_storage.go:CreateBodyStorageFromReader`；不能把一次改三项归为某单项收益；禁止清空生产Redis |

缓存对照需额外注意：当前内存选路和数据库选路的权重处理不同。可先用单渠道隔离缓存成本，避免开/关缓存时同时改变渠道分布。系统监控/限流开关也应逐项变化。

没有现成关闭开关的内置保护，先量化其行为及资源上界；要声称“改善多少”，再使用隔离实验版本或只包含该修复的版本对照。不能用性能微基准替代完整请求测试。

## 6. 第一轮优先执行的三个实验

### 实验A：分流是否减少单路过载

固定同模型、同分组、同优先级A/B两个模拟上游，禁用亲和、跨组、指定渠道和自动摘除，重试设0。保持A/B总容量、响应长度和耗时不变。

控制组设置明显偏向A的权重，实验组按事先测得的容量比例分配。模拟上游有真实执行的容量阈值：超过在途上限或请求配额时返回约定429，其余请求按既定时序完成。请求样本包含有代表性的短/长输入与流式时长，不能全部瞬间返回。

逐级提升到达速率，比较同一档位的完成率、有效吞吐和A/B负载。单渠道对比双渠道可作为额外实验，但标题应为“增加渠道资源并分流的综合收益”，不能称作纯算法收益。

### 实验B：一次重试能补救多少失败

在网关与备用均有余量的负载下，A作主渠道、B作低优先级备用，注入A的固定故障时段。分别测试重试0次和1次，保留相同故障时间表、请求到达表与其他配置。

先注入首个业务输出之前的可重试HTTP故障，再独立测试流中断；已发送部分响应不能默认能够无损重放。报告最终失败率和额外调用数，并补测A/B共同故障以识别重试放大。不要把模拟独立随机失败下的理论概率当实测。

### 实验C：限流是否保护正常用户

固定多个独立正常测试用户的低速流量，同时向一个独立用户注入突发高流量。分别测试用户总请求桶关闭/开启，其他窗口限制固定为不干扰实验的配置。

报告正常用户完成率、异常用户被拒绝量及全量未成功率。正常组在两轮中的流量和期限完全相同。还要覆盖所有用户一起增加流量的场景，验证单用户桶不能代替全局容量控制。

## 7. 负载、重复与观测流程

1. 对照运行配置，少量冒烟请求验证协议、额度、路由、流结束、错误注入和各层计数一致。
2. 从低速预热，按服务器实测承载情况逐档增加；例如1、2、5、10请求/秒只是起始设计示例，不是线上安全额度。每档先观测约5分钟，长请求/低失败率场景延长。
3. 记录到达RPS、实际在途请求数、完成RPS。稳定时在途量约为到达速率乘平均驻留时间，例如10请求/秒、平均10秒约有100个在途；不能把100并发等同100请求/秒。
4. 同条件至少重复3轮并交错运行控制/实验配置，保留所有结果；先预热再采样，故障注入和恢复使用相同相对时间。记录轮次波动，低失败率需足够样本及置信区间，不能挑最好一轮。
5. 固定发流窗口结束后停止新增请求，等待已有请求在预设期限内结束。逻辑请求结果按发出批次统计，不把尚未完成请求漏掉；稳态吞吐单独按稳态时间窗口统计。
6. 同时记录压测机、模拟上游与网关资源，确认压力瓶颈不在压测机或模拟上游的非预期限制。关联Nginx错误、网关错误类别、上游状态与时间段；单看502/503不能定位根因。
7. 事先定义停止条件：如测试实例持续超出配额、出现重启、错误持续超过实验上限或触及实际费用/上游额度预算；停发后记录恢复时间，不让负载无限增加。
8. 若需要长期稳定性结论，在容量范围内增加持续运行场景，观察资源增长与恢复。短时压力结果不能直接外推全天可用性。
9. 完成HTTP机制实验后，用固定Agent任务集执行业务对照：覆盖单轮响应、多轮模型调用及稳定的本地工具流程，保持模型/提示/客户端/工具/负载不变，只调整已选网关配置。所有导致调用最终失败的原因均纳入Agent失败率，另报告哪些属于网关/上游、哪些属于工具或客户端。HTTP实验收益不能直接外推为完整Agent收益。

不必先部署整套监控平台。最小证据由客户端逐请求记录、模拟上游逐尝试记录、入口/网关脱敏日志及固定间隔资源采样组成；已有监控可复用。MySQL连接等待、慢查询与Redis延迟用于定位，不以CPU利用率升高作为改进目标。
