# 单渠道与多渠道对照实验

日期：2026-09-05。用户要求把简历中的“提升模型调用稳定性”替换为单渠道到多渠道的量化效果。上一轮90:10与25:75的对照都属于多渠道，不能回答这个问题；本目录单独记录本轮实验。

## 执行前固定的条件

- 同一台服务器、同一应用镜像、同一独立SQLite/Redis/Nginx测试实例。
- 单渠道：仅A开启；B/C明确停用；不重试。
- 多渠道：A/B为优先级20的主渠道，权重25:75；C为优先级10的备用渠道；最多重试一次。
- A/B/C分别允许8/24/32个在途请求，超限即时429。成功流持续1秒，首个有效文本在约0.2秒发出。
- 场景一：持续20请求/秒，无注入故障。
- 场景二：同样20请求/秒，叠加A每10秒前2秒返回503；B/C持续健康。
- 每场景每方案重复3次、每次30秒，共12轮7200次正式请求。依次单/多、多/单、单/多；每轮另2次预热，不进入正式样本。
- 不调用真实模型供应商，不使用原服务数据库；所有测试身份都是独立生成，原始结果只记录测试ID、时间、状态和计数。

这比较的是增加上游容量与引入分流、备用、重试的整体方案。单渠道主容量8，多渠道主池容量32，另有32备用容量；不能把全部差异归于算法效率。单渠道配置是本次重建的对照，不是历史生产版本或配置快照。

## 文件与复核

- `tools/setup.py`：本轮实际隔离部署过程，使用原服务现存镜像，不重新构建产品代码。
- `tools/admin.py`：只允许操作恰好3个测试渠道；状态通过专用状态接口修改，配置及凭据分离。
- `tools/benchmark.py`、`tools/test_benchmark.py`：三渠道模拟上游、固定时间调度的流式请求端与契约测试。
- `tools/run_experiments.py`：固定参数、预热、两项场景、3次重复及状态保护。
- `tools/analyze.py`：独立检查生效配置、单渠道零分流、主渠道选择和备用重试顺序，并重新计算失败率及成功请求P95。
- `results/`：环境、预检、逐次客户端/上游记录、逐轮配置、汇总及清理结果。凭据和数据库不进入结果目录。

在此目录执行 `python3 tools/analyze.py results` 可以从原始样本重新生成汇总。工具内私网地址与资源名称针对本次临时部署；不要直接对原服务运行初始化脚本。完整结论以仓库 `docs/stability-single-vs-multi-results.zh_CN.md` 为准。

## 口径

失败率分母是逻辑HTTP模型请求数；重试增加的上游尝试数另计。成功要求收到有效文本和response.completed并结束流；429、503、网络异常、超时和流中断均计失败。延迟P95只统计完整成功的请求，并与失败率同时展示。零失败只表示本次样本没有观察到失败。

本轮是模拟容量和故障的隔离HTTP实验，没有真实Agent多步调用、真实模型故障分布或长期生产可用性证据。
