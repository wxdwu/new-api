# 锐捷 Codex 适配改动总结

> 本文基于仓库 `main` 分支截至 2026-08-13 的代码与 Git 历史整理，说明锐捷版本相较于最初 new-api 上游快照增加的主要能力、关键提交、接口链路和当前已知问题。

## 1. 项目定位

原始 new-api 是一个通用 AI API 网关和运营管理平台，主要提供：

- OpenAI、Claude、Gemini、Azure、AWS Bedrock 等多种上游模型的统一接入；
- OpenAI 兼容的 `/v1/*` 模型接口；
- 渠道选择、模型映射、负载均衡和失败重试；
- 用户、API Token、权限、分组和限流；
- Token、图片、音频、视频等用量计费；
- 渠道、用户、额度和日志管理后台。

锐捷版本没有重写上述核心能力，而是在其上增加了一套面向锐捷 Codex 的服务端适配层，使本项目同时承担以下角色：

1. 锐捷 Codex 的 OAuth/OIDC 身份服务；
2. 锐捷 SSO 与 Codex Desktop 之间的登录桥梁；
3. Codex Backend 兼容接口；
4. Codex 用户的钱包、额度和账单服务；
5. Plugin、Connector、WHAM 和部分 MCP 兼容接口；
6. 模型发现、Reasoning 能力描述和展示控制；
7. Skill、Tool、MCP 和 API Key 使用统计。

因此，当前项目可以概括为：

> 锐捷 Codex 的身份认证中心、模型网关、计费中心和部分桌面服务兼容后端。

需要注意，本仓库不是 Codex Desktop 本身。桌面端负责本地文件、终端、Git、Agent 循环、浏览器启动和本机 OAuth 回调；本项目负责身份、接口、模型转发、账户和计费。

| 方向 | 原始 new-api | 锐捷主要增加内容 |
| --- | --- | --- |
| 项目定位 | 通用 AI API 网关 | 锐捷 Codex 服务端中枢 |

## 5. 锐捷 SSO 与 Codex 登录闭环

原始 new-api 已经支持通用自定义 OAuth Provider。锐捷没有重写这一整套机制，而是在其上增加了 `slug == "ruijie"` 的专用入口、自动登录、品牌页面和 Codex 授权回跳。

完整链路包含两层 OAuth：

```text
第一层：锐捷 SSO → 登录 new-api Web Session
第二层：new-api OAuth Server → 向锐捷 Codex 发放 OAuth Token
```

### 5.1 完整流程

```text
1. 锐捷 Codex Desktop 启动本地回调服务 localhost:1455。
2. Desktop 打开浏览器访问 new-api 的 /oauth/authorize。
3. new-api 检查浏览器 Session；未登录则跳到 /sign-in，并保存原授权地址。
4. 登录页读取 /api/status 中 slug=ruijie 的自定义 OAuth Provider。
5. 前端请求 /api/oauth/state，生成防 CSRF state。
6. 浏览器跳转锐捷 SSO authorization_endpoint。
7. 锐捷 SSO 回调 new-api 的 /oauth/ruijie?code=...&state=...。
8. SPA 页面调用 /api/oauth/ruijie，把 code 和 state 交给后端。
9. new-api 用 code 调用锐捷 SSO token_endpoint，再调用 user_info_endpoint。
10. new-api 根据锐捷用户 ID 匹配或创建用户，建立浏览器 Session。
11. 浏览器重新进入原来的 /oauth/authorize。
12. 用户批准后，new-api 创建一次性授权码并 302 到 localhost:1455。
13. Codex 收到 code 后调用 /oauth/token，并携带 PKCE code_verifier。
14. new-api 返回 access_token、id_token 和 refresh_token。
15. Codex 使用 Bearer access_token 调用模型和账户接口。
```

### 5.2 两个不同的回调地址

必须区分：

| 回调 | 作用 |
| --- | --- |
| `https://<new-api域名>/oauth/ruijie` | 锐捷 SSO 回调 new-api |
| `http://localhost:1455/auth/callback` | new-api 最终回调 Codex Desktop |

## 6. OAuth 凭证与钱包计费

### 6.1 `codex-token` 桥接

用户批准 Codex OAuth 授权时，系统会调用 `GetOrCreateNamedUserToken` 创建或恢复名为 `codex-token` 的普通 new-api Token。

其作用是兼容原有 API Token 和 Relay 体系。相关提交包括：

- `10451833b`：补充 `GetOrCreateNamedUserToken`；
- `e5ace7222`：鉴权兼容 `sk-oauth-` 前缀；
- `d61d870ed`：Token 过期时间或状态异常时自动恢复。

### 6.2 OAuth JWT 鉴权

提交：

```text
e1db6519f fix: TokenAuth 支持 OAuth JWT 兜底
```

改造后，模型接口可以同时识别：

```text
Authorization: Bearer sk-...
Authorization: Bearer <OAuth JWT>
x-api-key: ...
```

### 6.3 按用户钱包计费

核心提交：

```text
ee68dbaaa fix: align Codex OAuth billing with user wallet
```

该提交解决 OAuth Access Token 和普通 API Token 数字 ID 可能碰撞导致的串账问题。

计费规则变为：

- OAuth 请求按照已认证用户的钱包 `quota`、`used_quota` 计费；
- 普通 API Token 请求继续使用 Token 维度额度和统计；
- OAuth Access Token ID 不再放入会被解释为 `model.Token.Id` 的上下文字段；
- OAuth 请求预扣费和结算会更新用户钱包，但不会误更新同 ID 的普通 API Token；
- `/v1/dashboard/billing/subscription` 和 `/usage` 对 OAuth 返回用户钱包数据；
- 回归测试覆盖 OAuth Token ID 与普通 API Token ID 冲突的情况。

主要文件：

- `constant/context_key.go`
- `middleware/auth.go`
- `controller/billing.go`
- `relay/common/relay_info.go`
- `service/billing_session.go`
- `service/quota.go`

```text
preserve local customizations (锐捷Api, tag index, OAuth plugins)
```

因此后续维护应把代码分为三类：

1. new-api 上游通用能力；
2. 锐捷 Codex 定制能力；
3. 为解决上游同步冲突而产生的兼容修改。

不能仅依据“当前版本相对初始版本的总 Diff”判断锐捷工作量，否则会把上游前端重构和模型支持更新误算成锐捷功能。

## 14. 已知问题和风险

### 14.1 Codex 模型表迁移

`model.CodexBackendModel` 当前没有进入主 AutoMigrate 列表。全新数据库调用 Codex `/models` 时可能因缺少 `gpt_codex_models` 表失败。

### 14.2 SSO 回跳参数可能丢失

当前登录页已经读取 `redirect`，但锐捷主按钮调用 `startRuijieLogin()` 时没有继续传递该参数，专用 Hook 调用 `handleCustomOAuthLogin(ruijieProvider)` 时也未传 `redirectTo`。

首次 Codex OAuth 登录可能出现：

```text
Codex 授权页
→ 锐捷 SSO
→ SSO 成功
→ 进入 Dashboard
→ 没有回到原 /oauth/authorize
→ Codex 等不到 localhost 回调
```

应让 `startRuijieLogin` 接收并继续传递原始 redirect。

### 14.3 回调 URL 暴露普通 API Token

批准授权时，当前实现会在本地回调 URL 中附加：

```text
codex-token=sk-...
```

完整 API Token 可能进入浏览器历史、反向代理日志、访问日志或 Referer。更安全的方式是使用一次性兑换码，或者只通过 `/oauth/token` 返回 OAuth 凭证。

### 14.4 Tool 统计接口鉴权

部分 Tool 统计接口当前只有限流，没有明确的管理员或用户鉴权。统计详情可能包含用户名、Token 名称、模型、额度和日志 ID，应补充权限控制。

### 14.5 PostgreSQL Tag 查询

存在类似：

```go
Where("tag = \"1\"")
```

的查询。在 PostgreSQL 中双引号通常表示标识符，可能被解释为列名 `"1"`。应使用 GORM 参数绑定。

### 14.6 插件和 MCP 完成度

- 插件安装主要写数据库状态；
- Workspace 和 Share 等接口有桩实现；
- MCP `tools/list` 当前为空；
- 本项目尚不是完整的远程插件/MCP 执行平台。

### 14.7 Docker 部署不一定包含锐捷代码

主 `docker-compose.yml` 仍引用上游镜像 `calciumion/new-api:latest`。直接执行该 Compose 可能运行上游版本，而不是当前锐捷分支代码。

生产部署应明确使用：

- 本仓库构建的镜像；或
- 明确包含锐捷提交的已发布镜像。

同时不应在生产环境沿用示例中的数据库、Redis 默认密码和公开数据库端口。

### 14.8 数据库迁移日级跳过

AutoMigrate 使用每日标记跳过重复迁移。同一天多次发布且第二次包含新表结构时，可能跳过必要迁移，需要结合发布流程重新评估。

### 14.9 OAuth 签名密钥和 Issuer

- 多实例部署必须共享签名私钥，否则不同实例签发的 JWT 无法互认；
- 应显式设置 `OAUTH_SERVER_ISSUER` 或正确的 `ServerAddress`；
- 不应依赖第一次请求的 Host 推导生产 Issuer。

## 17. 总结

从 Git 提交演进可以看出，锐捷适配主要围绕以下主线展开：

```text
通用 new-api 模型网关
        ↓
增加 Codex Backend 和 OAuth Server
        ↓
串联锐捷 SSO 与 Codex Desktop 本地回调
        ↓
让 OAuth 用户接入 new-api 钱包和计费
        ↓
补充 Plugin、WHAM、模型发现和 Reasoning 元数据
        ↓
增加 Skill、Tool、MCP、API Key 使用统计
        ↓
完成锐捷 AI Workspace 和 TokenHub 产品化界面
```

最终形成的不是简单的登录页换皮，而是一套在 new-api 网关底座之上的锐捷 Codex 服务端适配层。它已经覆盖身份、模型、账户、计费和部分插件接口，但插件执行、部分 Codex 云服务接口、迁移可靠性和登录安全仍有进一步完善空间。
